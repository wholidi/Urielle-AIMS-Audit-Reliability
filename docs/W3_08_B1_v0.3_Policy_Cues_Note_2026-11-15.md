# W3-08 — B1 v0.3: cue lists inside the hashed policy (proposal)

**Status:** `PROPOSED_NOT_APPROVED` · engineering only · adds new files; v0.1 and v0.2 files are untouched.

## Change relative to b1-0.2.0 (`src/b1_consistency_check_v3.py`, `b1-0.3.0`, policy id `b1-lexical-v3`)
`negation_cues`, `negation_phrases`, `hedge_cues` and `number_words` are now `B1Policy` fields. Changing any of them changes `policy_sha256` (tested), and the judge reads them from the policy, not from module constants. Default values equal the v0.2 constants, so default behaviour is unchanged: the same 11 adversarial cases are non-SUPPORTED, `SYN-S03` is still a known limitation.

## Hedge-cue breadth check (7 hand-written, legitimately supporting evidence texts that contain a hedge-list word; claim unhedged)
Outcome: 5 of 7 were **not** SUPPORTED (2 AMBIGUOUS, 3 INSUFFICIENT); 2 were SUPPORTED (one because the claim itself contains the hedge word `pilot`). A hedge word anywhere in the best sentence (for example "…reviewed annually" with `will`, "…subject to annual review", "…could be extended later") disqualifies it.
This is a small, hand-picked sample and not a rate estimate. It shows the hedge rule is **blunt**: it trades false rejections for blocking future/conditional support. Options for the research lead: keep (fail-safe), narrow `hedge_cues` (for example drop `will`, `if`, `subject`, `could`, `draft`), or score hedging only on the clause containing the claim's terms. No change made here.
